# Обновление 1.6.0: три связанные базы данных

Добавлены отдельные базы `users.db` (аккаунты), `tables.db` (сохранённые таблицы)
и `documents.db` (исходные текстовые документы). Базы создаются автоматически
в каталоге данных; прежние аккаунты из `secure_shell.db` переносятся при запуске.

Новая вкладка **«Библиотека»** позволяет администраторам хранить и редактировать
исходники, конвертировать их и сохранять результаты. Обычные пользователи видят
только разрешённые таблицы; исходные документы доступны только администраторам.
Вкладка **«Учётные записи»** служит для управления пользователями и их правами.

[Запуск, форматы данных, связи и резервное копирование](DATABASES.md).

# Создание администратора

Для создания аккаунта `admin_admin` с паролем `12345678` закройте приложение и
однократно запустите **Создать администратора.bat**. Затем откройте **Запустить.bat**.
Команда использует тот же каталог данных, что и обычный запуск, включая
`SECURE_SHELL_DATA_DIR`, если он задан. При необходимости exe пересобирается;
для сборки нужны Python 3.10+ и интернет.

Создание допускается только в пустой базе. Повторный запуск не меняет пароль
существующего аккаунта. Если admin_admin уже существует с другим паролем либо
заблокирован, появится сообщение, данные сохранятся. Пароль хранится в базе
как PBKDF2-хеш с индивидуальной солью. Обычный запуск не создаёт этот аккаунт
автоматически и не восстанавливает заданный пароль после его смены.

# Обновление 1.5.0: отображение таблиц

Вкладка **«Таблицы»** показывает ведомость с многострочной шапкой, объединёнными
ячейками, цветными разделителями групп и разделов, итогами и прокруткой. Кнопки
**−** и **+** меняют масштаб. При входе отображается нейтральный образец.

Чтобы создать свой первый файл, зарегистрируйте каталог во вкладке
**«Файлы и редактор»**, выделите его и нажмите **«Создать образец таблицы»**.
Создаётся `Пример таблицы.json`, открываемый через файловый сервис с проверкой
прав. Его можно редактировать как обычный текст UTF-8 и сохранить, затем
выделить в проводнике и нажать **«Показать как таблицу»**. Файл образца также
включён в архив как `examples/report-template.json` для просмотра структуры.

Формат JSON: `format` равен `secure-shell-table-v1`; поля `title`, `subtitle`,
`summary` задают заголовки и общий итог. Массив `sections` содержит разделы с
`title`, необязательным `summary` и массивом `groups`. В каждой группе есть
`title` и `rows`; каждая строка содержит ровно 13 строковых ячеек в порядке
заголовков экрана. Совпадающий текст соседних строк группы в некоторых столбцах
автоматически объединяется. Ограничения: до 1 МиБ на файл, до 400 строк
ведомости. Таблицы доступны только для просмотра; содержимое меняется через
текстовый редактор. При отзыве прав или выходе данные удаляются из окна.

# Обновление 1.4.0: проводник и текстовый редактор

После входа откройте вкладку **«Файлы и редактор»**. Администратор может нажать
**«Зарегистрировать каталог…»**, выбрать существующий каталог, направление и уровень
доступа. Файлы, созданные вне программы, не появятся в проводнике, пока их
метаданные не будут зарегистрированы через файловый сервис. Для нового каталога
используйте **«Новая папка»**, для файла — **«Новый текстовый файл»**.

Двойной щелчок по файлу открывает его через проверку прав. Редактор работает с
обычным текстом UTF-8 размером до 2 МиБ; при некорректной кодировке, двоичном
содержимом или превышении лимита файл не открывается. **«Сохранить»** вызывает
защищённый файловый сервис; обнаруженное изменение исходника извне блокирует сохранение.
Проверка не гарантирует защиты от записи другого процесса между сравнением и заменой.
Незавершённые правки запрашивают подтверждение при переходе к другому файлу.
После выхода либо отзыва сеанса текст и список каталогов удаляются из окна.
Права проверяются при каждой операции, поэтому изменение прав начинает действовать
без перезапуска. На Windows перед применением проверьте запуск и сборку EXE.

# Обновление 1.3.0: защищённое чтение и сохранение файлов

Файловый сервис теперь содержит операции с содержимым, которые проходят через
тот же контроль направления и уровня секретности, что и удаление/переименование.

- `read_bytes()` / `read_text()` читают только зарегистрированные обычные файлы и
  после успешного чтения создают событие `FILE_OPEN`. Для редактора можно задать
  `max_bytes`, чтобы не загружать в память файл больше разрешённого размера.
- `create_file()` / `create_text_file()` создают новый файл только внутри доступного
  зарегистрированного каталога. Новый объект наследует `direction_id` и
  `secrecy_level_id` родителя; существующий файл никогда не перезаписывается.
- `write_bytes()` / `write_text()` сохраняют только уже зарегистрированный и доступный
  файл. Содержимое сначала записывается во временный файл рядом с исходным и затем
  заменяется через `os.replace`, поэтому ошибка до замены не портит исходник.
- Успешное создание и сохранение фиксируются как `FILE_CREATE` и `FILE_SAVE`.
  Неизвестные метаданные по-прежнему означают отказ в доступе.

Версия 1.3.0 подготовила сервисный API для графического интерфейса.

# Обновление 1.2.0: контроль подключения

- При входе администратора начинается опрос, затем повторяется каждые **5 минут**.
  Каждому открытому обычному сеансу выдаётся отдельный запрос. Клиент отвечает автоматически
  при очередном обновлении окна (примерно раз в 2 секунды); нажимать кнопку не требуется.
- На ответ даётся **60 секунд**. Пропуск хотя бы одним сеансом блокирует аккаунт,
  отзывает все его сеансы и сохраняет событие `NETWORK_BLOCK`. Поздний ответ не снимает блокировку.
  На работающем клиенте окно входа появится при ближайшей проверке; остановленный процесс
  узнает об отзыве после возобновления. Обычный выход до истечения запроса не блокирует аккаунт.
- Блокировка сохраняется после перезапуска. Администратор снимает её в таблице
  **«Подключения пользователей…» → «Разблокировать выбранного пользователя»**.
  Снятие блокировки требует нового входа, старые сеансы не восстанавливаются.
- Табло открывается автоматически при наличии недоступных пользователей и обновляется каждые
  **10 минут** (первое обновление при входе администратора); кнопка обновляет его немедленно.
  В таблице есть горизонтальная и вертикальная прокрутка, последний вход, последний сигнал
  и до пяти последних файловых действий с временем UTC. Учтены также никогда не входившие,
  заблокированные и деактивированные аккаунты. Текущий администратор исключён из списка.
- Административные аккаунты показываются в табло, но автоматически не блокируются,
  чтобы сохранить возможность восстановления. Одновременные окна администратора не
  создают повторных запросов. Для опроса должно оставаться открытым хотя бы одно окно
  с действующим сеансом администратора; фоновой системной службы нет.

**Граница реализации:** транспорт запросов и ответов — общая база SQLite текущего проекта.
Все экземпляры должны работать с одной базой (`SECURE_SHELL_DATA_DIR`). Отдельные локальные
копии баз не обмениваются сигналами. Это не готовая распределённая система: для опроса
разных компьютеров нужен отдельный сервер с аутентифицированным сетевым протоколом.
Не переносите SQLite на сетевой диск в качестве замены такому серверу. Успешный ответ
подтверждает доступность приложения/базы, а не отсутствие атак или целостность всей сети.
Пользователь с прямым доступом на запись к SQLite может изменить данные мониторинга;
база рассчитана на доверенное локальное окружение, не на защиту от администратора ОС.
Файлы, запущенные или изменённые вне приложения, в эту историю не входят.
Если сама база недоступна, клиент закрывает локальный сеанс; запись блокировки возможна
только после восстановления доступа администратора к базе.

При обновлении распакуйте проект поверх предыдущей версии, сохранив каталог данных,
и откройте `Запустить.bat`: изменение APP_VERSION вызывает повторную сборку exe.
Схема существующей базы обновляется автоматически. Windows-сборка в Linux не проверена.

# Secure Shell — исправленные модули

Исправлены предоставленные исходники. Это не готовая сборка Windows и не исправление
`script2.exe`: соответствие этих исходников тому исполняемому файлу не установлено.
Добавлено новое окно PyQt5 `src/ui/login_window.py`: настройка первого администратора,
вход, сведения о пользователе, смена пароля и завершение сеанса. Это стартовый
интерфейс; рабочий стол, проводник, редакторы и панель администрирования ещё не созданы.

## Команда «компрометация» (версия 1.1.0)

Функция «Показать пароль» удалена. Поля паролей всегда маскированы.
Администратор получает две новые кнопки; обычному пользователю они недоступны.

1. Войдите как администратор и нажмите **«Подготовить резервные пароли…»**.
2. Задайте отдельную парольную фразу минимум из 12 символов и выберите новый файл.
   Приложение создаст уникальный пароль для каждого активного аккаунта: ровно
   50 символов, только ASCII-цифры и знаки, обязательно оба типа символов.
   Используется криптографический генератор `secrets`.
3. Пароли сохраняются в выбранный файл с шифрованием AES-256-GCM; ключ получается
   из фразы через scrypt с индивидуальной солью. В БД для сброса остаются только
   PBKDF2-хеши. В журнал пароли и парольная фраза не записываются.
4. **До сброса проверьте файл**: откройте `Резервные пароли.bat` (либо
   `python src/main.py --recover`), выберите файл и введите фразу. Просмотр работает
   без авторизации в приложении, но требует расшифрования. Сохраните файл и фразу
   раздельно. Без фразы восстановить содержимое файла невозможно.
5. Нажмите **«компрометация»** и подтвердите действие. Пароли всех активных учётных
   записей заменятся на подготовленные, а все открытые сеансы в этой базе будут
   отозваны, включая сеанс администратора. Сохранённые состояния окон удаляются,
   счётчики блокировки входа сбрасываются.
6. Войдите по резервному паролю. Набор используется однократно. Подготовьте новый
   набор для следующего инцидента. При добавлении/деактивации аккаунта требуется
   заново подготовить полный набор. Предыдущий файл сохраняется, но новый набор
   заменяет его назначение в БД.

Команда действует на **экземпляры новой версии, подключённые к одной SQLite-базе**.
Перед обновлением закройте старые версии на всех рабочих местах и запустите новые.
Разные локальные копии БД не синхронизируются. Окна проверяют сеанс примерно раз
в две секунды и возвращаются ко входу; проверки сервиса также отклоняют отозванный
сеанс. Уже запущенные внешние процессы эта команда не завершает.

### Отчёт активности

Отчёт сохраняется в таблице `emergency_reports` в одной транзакции со сбросом.
Дополнительно создаётся JSON-файл `~/.secure-shell/incident-reports/<ID>.json`
(или внутри SECURE_SHELL_DATA_DIR). Если экспорт файла не удался, UI показывает
ID отчёта в БД; сброс остаётся выполненным. Ошибка записи отчёта в БД отменяет
всю операцию сброса. Поля отчёта:

- учётные записи, чей пароль сброшен;
- незавершённые сеансы: время входа UTC, последнее обращение, длительность до
  команды, признак свежего обращения за последние 30 секунд;
- вся сохранённая история действий аккаунтов с такими сеансами;
- `executable_path` — путь исполняемого файла для зарегистрированного события;
- `transfer_source` и `transfer_destination` — исходный и целевой пути для
  зарегистрированных операций; переименование/перемещение файла заполняет их.

При входе регистрируется исполняемый файл самого приложения (`SESSION_PROCESS`).
События запуска других файлов и передачи можно записать через
`AuditLogger.log_execution()` и `log_transfer()` из соответствующего доверенного
сервиса после успешной операции. В текущем интерфейсе запуск других программ и
сетевые передачи не реализованы. **Мониторинга процессов Windows, внешнего
сетевого трафика и программ вне приложения нет.** Пустое поле означает отсутствие
зарегистрированных сведений, а не доказательство отсутствия действия.

Длительность — время открытого сеанса вместе с простоем. Аварийно закрытая программа
может оставить незавершённый сеанс: смотрите последнее обращение и признак свежести.
Исторические сеансы до установки этой версии не восстанавливаются. Паролей в
отчёте нет; сам отчёт содержит логины и пути и должен храниться с рабочими данными.

## Быстрый запуск на Windows

Распакуйте весь архив и дважды щёлкните `Запустить.bat`.
Если `SecureShell.exe` отсутствует, скрипт создаст отдельное окружение `.venv-build`,
установит PyQt5 и PyInstaller, соберёт `SecureShell.exe` и откроет приложение.
При первой сборке нужны Python 3.10+ для Windows и интернет. Для установки Python
можно использовать официальный установщик; при установке включите Python Launcher
или добавление Python в PATH.

После успешной сборки открывайте `SecureShell.exe` напрямую. Готовый EXE включает
Python, PyQt5 и схему БД; отдельная установка Python для его запуска не требуется.
Для пересборки после изменения исходников запустите `build_windows.bat` из командной
строки. `Запустить.bat` проверяет APP_VERSION и пересобирает EXE при смене версии.
Для произвольных правок исходников пересоберите вручную.
Данные остаются в `~/.secure-shell`, отдельно от EXE.

В этом архиве находятся исходники и скрипты сборки. Готового EXE пока нет:
сборка Windows не выполнялась в Linux-среде подготовки проекта.

## Настройка

Требуется Python 3.10+. Из корня распакованного проекта:

```sh
python -m venv .venv
# Windows: .venv\Scripts\activate
# Linux/macOS: source .venv/bin/activate
python -m pip install -r requirements.txt
python src/main.py
```

При первом запуске окно настройки запрашивает новый пароль администратора
`admin_admin`. Общего пароля по умолчанию больше нет. Повторная настройка непустой
базы запрещена. Пароль не передаётся в аргументах командной строки.

По умолчанию данные находятся в `~/.secure-shell`. Для другого расположения задайте
`SECURE_SHELL_DATA_DIR` перед запуском. Не используйте каталог исходников или
установки приложения для рабочих данных.

Для последующих запусков:

```sh
python src/main.py
```

Альтернатива графической настройке: `python src/bootstrap.py`.

## Проверки

Для всех проверок установите зависимости из requirements.txt. Без PyQt5 проверки интерфейса будут пропущены:

```sh
python -m unittest discover -s tests -v
```

Тесты используют временные каталоги и базы. Проверяют регистрацию, блокировку входа,
актуальность прав, деактивацию, миграцию схемы и паролей, внешние ключи, файловые
операции, откат при ошибке файловой системы и отсутствие дублирования логов.

## Изменения API для подключения интерфейса

- Пакет `logging` переименован в `app_audit`. Замените импорты
  `from logging.audit_logger import AuditLogger` на
  `from app_audit.audit_logger import AuditLogger`. Старую папку `src/logging`
  удалите при переносе исправлений в полный проект: она перекрывает stdlib.
- `LoginManager.current_user` — свойство только для чтения. Для входа и выхода
  используйте `login()`/`logout()`. Права перечитываются из БД при каждом обращении.
- `register_user()` требует действующей административной сессии. Первого
  администратора создаёт окно первоначальной настройки либо локальная процедура `bootstrap.py`.
- `delete_user()` теперь деактивирует учётную запись и удаляет сохранённую сессию.
  Владелец файлов и журнал остаются связаны с существующей учётной записью.
  Деактивированные логины не переиспользуются; физическое удаление не выполняется.
- Последнего активного администратора нельзя понизить. Самоудаление запрещено.
- Файловый сервис больше не статический:

```python
from file_manager.file_ops import FileOperations
files = FileOperations(db_manager, login_manager)
files.list_directory(path)
files.delete_file(path)
```

  Обрабатывайте `PermissionError`, `OSError`, `sqlite3.Error` в UI и показывайте
  ошибку пользователю. Ошибки больше не маскируются пустым списком или `False`.
  В обработчиках GUI не вызывайте `os.remove`/`os.rename` напрямую.
- Администратор регистрирует существующий рабочий каталог через
  `files.register_directory(path, direction_id, secrecy_level_id)`.
  `create_directory()` наследует метки родителя. Неизвестные метаданные означают
  отказ в доступе. Файлы из будущего редактора также должны получать метаданные
  через доверенный сервис до предоставления доступа.
- `rename_file()` поддерживает обычные файлы в одной файловой системе; целевой
  файл не перезаписывается. Каталоги не переименовываются. Перенос между разными
  направлениями или метками секретности запрещён.
- Чтение и запись содержимого реализованы через `read_bytes()` / `read_text()` и
  `write_bytes()` / `write_text()`. Новые файлы создавайте только через
  `create_file()` / `create_text_file()`, чтобы метки доступа наследовались от
  родительского каталога. Редакторы и рекурсивные операции в GUI пока не добавлены.

## Миграция существующей базы

1. Закройте все экземпляры приложения и сделайте резервную копию рабочей БД.
2. Укажите её каталог через `SECURE_SHELL_DATA_DIR`. При переходе с прежней
   версии `secure_shell.db` копируется в `users.db`, если новой базы ещё нет.
3. Создаются также `tables.db` и `documents.db`; схема аккаунтов обновляется
   автоматически. Существующие пользователи, файлы и журналы сохраняются.
   Подробности и резервное копирование всех трёх баз описаны в [DATABASES.md](DATABASES.md).
4. Если найдены нарушения внешних ключей, запуск прекращается с объяснением.
   Автоматическое удаление повреждённых записей не выполняется. Сначала исправьте
   связи на копии БД. Изменения схемы могут быть уже применены до этой проверки.
5. Старые хеши SHA-256 проверяются и заменяются на PBKDF2 при успешном входе.
   Существующие пароли автоматически не меняются. Если ранее использовался общий
   пароль `12345678`, смените его перед дальнейшей работой.
6. Метаданные новых объектов используют абсолютный нормализованный путь.
   Старые относительные или иначе записанные пути автоматически не угадываются:
   приведите их к фактическим абсолютным путям в копии БД. До этого доступ к ним
   может быть запрещён. Символические ссылки и поддерживаемые Python junction
   отклоняются.

## Границы проверки

- Проверены все 120 тестов, включая авторизацию, три базы, миграцию, конвертацию,
  административные права и настоящие виджеты PyQt5 в режиме offscreen (Linux).
  Проверки Windows и сборка EXE не выполнялись. Диапазоны зависимостей в requirements
  согласованы с setup.py; установку следует проверять в целевой Windows-среде.
- Низкоуровневый доступ к БД/файлам должен быть закрыт правами ОС. Это приложение
  не заменяет разграничение доступа Windows. Проверки путей предполагают, что
  посторонний процесс не изменяет файлы и каталоги во время операции.
- SQLite и файловая система не образуют общую транзакцию. При обычных ошибках
  операции пытаются откатить изменения; внезапное завершение процесса может
  потребовать сверки БД и файлов. При удалении остатки `.pending-delete-*` требуют
  проверки администратором; ошибка очистки явно регистрируется.
- Неудачные входы известных пользователей пишутся в БД и файл. Для неизвестного
  логина событие пишется в файл без фиктивного `user_id`.
- Счётчики блокировки сохраняются в БД; после трёх ошибок вход закрывается на
  пять минут. Сброс пароля администратором снимает блокировку учётной записи.
- Пакет содержит `schema.sql`, `storage_schema.sql` и `storage_links.sql` для установки через setup.py. Сборка PyInstaller
  потребует явного включения SQL и ресурсов для целевой сборки.
